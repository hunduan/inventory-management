## 二、架构概览

### 2.1 后端架构

```
backend/src/
  main.ts                          # 入口：CORS、ValidationPipe、Swagger
  app.module.ts                    # 根模块，注册全局 Guard/Filter
  common/                          # 共享基础设施
```

**模块列表**: auth / products / categories / suppliers / customers / warehouses / purchases / sales / inventory / stocktake / transfers / reports / upload / tenants / users

## 三、代码质量分析

### 3.1 TypeScript 类型安全

| 指标 | 后端 | 前端 |
|------|------|------|
| `any` 类型出现次数 | 26 处 | ~90 处 |
| `strict: true` 配置 | 是 | 是 |
| 实际类型安全性 | 中等 | 差 |

**后端 `any` 问题**:
- 所有控制器的查询参数类型为 `any`（如 `purchases.controller.ts:18`）
- `as any` 强制转换在 DTO 和数据库查询中频繁使用（如 `products.service.ts:48,53`）
- `JWT_EXPIRES_IN` 被强制转换为 `as any`（`auth.module.ts:18`）

**前端 `any` 问题**:
- 所有 `services/*.ts` 中的 API 方法返回 `Promise<any>`
- 所有页面组件的状态类型为 `useState<any[]>()`
- 错误处理全部使用 `err: any`
- 缺少领域实体接口定义（无 `Order`、`Product`、`ApiResponse<T>` 等）

### 3.2 代码重复

**后端重复**:
- 4 个 CRUD 服务（suppliers、customers、warehouses、categories）代码几乎完全相同
- 订单号生成逻辑在 PurchasesService 和 SalesService 中完全重复
- 8 个控制器中没有 DTO（categories、suppliers、customers、warehouses 直接在 @Body 中使用 `any`）

**前端重复**:
- 分页组件在 **4 个页面中重复实现**（products、purchases、sales、inventory）
- 状态徽章在 **4 个文件中重复定义**（purchases、sales、mini/orders/list、mini/orders/detail）
- 登录页面在 Web 和小程序端 **95% 代码相同**
- 表格结构在 5+ 个页面中重复实现
- 过滤栏（搜索 + 下拉 + 按钮）在 4 个页面中重复

### 3.3 样式系统

**问题**: 大量内联样式，CSS 变量名存实亡

| 指标 | 计数 |
|------|------|
| `#0f766e` 硬编码出现次数 | 50+ 次（应为 `var(--primary)`） |
| `'1px solid #e7e5e4'` 硬编码 | 30+ 次（应为 `var(--border)`） |
| `#f5f5f4` 硬编码 | 20+ 次（应为 `var(--bg)`） |

app.less 定义了 `.button-primary`、`.button-secondary` 等工具类，但页面极少使用。小程序页面完全使用内联样式，不引用任何 CSS 类。

### 3.4 错误处理

**后端**: ★★★★☆ 良好
- 全局异常过滤器统一处理，返回 `{ success, data, error, timestamp }` 格式
- 业务逻辑中适当使用 `NotFoundException`、`BadRequestException`
- 无需 try/catch 包装（全局过滤器统一处理）

**前端**: ★★☆☆☆ 需改进
- 大量空 `catch { /* ignore */ }` 块，吞掉运行时错误
- `app-shell.tsx` `init()` 中 `JSON.parse()` 无 try/catch 保护
- 401 检测依赖字符串匹配 `err.errMsg?.includes('401')`，脆弱

### 3.5 测试覆盖

**覆盖率: 0%**

尽管 `package.json` 中配置了完整的测试框架（jest、@nestjs/testing、supertest），但代码库中没有任何测试文件。

## 四、安全性分析

### 4.1 认证与授权

| 检查项 | 状态 | 说明 |
|--------|------|------|
| JWT 认证 | 通过 | 15 个控制器中 14 个正确应用 `@UseGuards(JwtAuthGuard)` |
| 权限系统 | **形同虚设** | `@Permissions()` 装饰器定义了但从未使用，RolesGuard 永远返回 true |
| JWT 密钥 | **风险** | 未设置环境变量时回退到硬编码 `'dev-secret'` |
| 密码复杂度 | 弱 | 仅要求 `@MinLength(6)` |
| 用户禁用检查 | **缺失** | JWT 策略不验证用户是否仍启用，已禁用用户可用旧 Token 访问最多 7 天 |

### 4.2 租户隔离

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 查询级过滤 | 通过 | 所有服务通过 `@TenantId()` 装饰器获取租户 ID |
| 原子更新 | 通过 | 使用 `updateMany({ where: { id, tenantId } })` 防 TOCTOU |
| TenantsService | **缺陷** | `findById()` 不检查 tenantId，任何人可通过 ID 查询任意租户 |

### 4.3 数据完整性

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 库存变更事务 | **严重** | 采购收货、销售发货、调拨完成、盘点完成均未使用 Prisma 事务 |
| 注册事务 | **缺陷** | 创建租户与创建用户之间无事务保护，可能产生孤立租户 |
| 库存扣减检查 | **缺陷** | 调拨时未检查源仓库库存是否充足，可导致负库存 |

### 4.4 网络安全

| 检查项 | 状态 |
|--------|------|
| CORS 限制 | **未限制**（`app.enableCors()` 无 origin 参数） |
| 速率限制 | 无 |
| Helmet/CSP | 无 |
| 文件上传认证 | **缺失**（uploadAudio 不传 tenantId） |

### 优先改进事项（按严重程度排序）

**P0 — 数据安全**:
1. 为所有库存变更操作添加 Prisma `$transaction` 包装
2. 修复调拨的库存充足性检查
3. 修复租户注册的事务原子性

**P1 — 安全加固**:
1. 移除 JWT 硬编码回退密钥，启动时检查必需环境变量
2. JWT 策略增加用户启用状态验证
3. 限制 CORS origin

**P2 — 代码质量**:
1. 定义共享类型接口（`ApiResponse<T>`、`PaginatedResponse<T>`、`Order`、`Product` 等）
2. 消除 `any` 类型（从 services 层和查询参数开始）
3. 提取重复组件（分页、状态徽章、过滤栏、数据表）
4. 将内联样式迁移到 CSS 变量 + 工具类

**P3 — 功能完善**:
1. 编写测试（优先覆盖库存业务逻辑）
2. 补充供应商/客户/仓库前端页面
3. 实现真实 OCR/语音识别或移除存根
