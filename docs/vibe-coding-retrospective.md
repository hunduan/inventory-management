# Vibe Coding 复盘与反思

## 项目回顾：进销存系统开发过程

### 时间线

项目从一个完整的开发计划开始，覆盖了技术栈选型、模块划分、阶段规划。然后进入密集的功能开发阶段。

### 暴露的问题

#### 1. 没有验证闭环

最典型的是 Prisma Schema 问题——修改了 `StocktakeItem` 添加 `tenantId` 和关联，但没有跑 `prisma validate` 验证。结果 `Tenant` 模型缺少反向关联字段，导致 Prisma Client 无法生成，整个后端返回 500 错误。前端表现为"新增供应商内部错误"，排查了很长时间才发现根本原因是**不相关的模块**（StocktakeItem）的 schema 问题。

> 教训：每次 Schema 变更后必须 `prisma validate`，不能等运行时才发现。

#### 2. 平台约束不了解就写代码

Taro 小程序开发中，反复遇到同一类问题：
- `display: 'flex'` 内联样式编译为空字符串
- `paddingHorizontal` / `shadowColor` 等 React Native 属性在 Taro CSSProperties 中不存在
- `gap` 在小程序中不生效
- 每个问题都是写完之后用户反馈"没有变化"才去排查

每次都是试错修复，而不是先了解平台限制再写代码。

#### 3. 反应式开发，缺少主动审查

开发模式基本是：
1. 用户提需求 → 写代码
2. 用户说"没有效果" → debug
3. 用户发现 bug → 修 bug
4. 循环

没有在写代码之后主动做 code review，没有测试，没有端到端验证。Prisma migration 文件创建后没有确认是否与 schema 一致，就推进到下一步。

#### 4. 上下文碎片化

多次上下文压缩导致丢失了关键的决策记录。比如：
- Taro CSS 限制的解决方案每次都要重新摸索
- 之前做过的修改被遗忘，导致重复工作
- 用户需求的完整背景在压缩后丢失，只能用摘要推测

#### 5. "继续"陷阱

用户频繁说"继续"，但这个指令太模糊。没有明确的"当前迭代完成"的信号，导致：
- 一个功能还没完全验证就开始了下一个
- Bug 修复和新功能混在一起提
- 没有清晰的发布节点

## 一个好的 Vibe Coding 应该是什么样的？

Vibe Coding 不是"随意编码"，而是**人机协作的高效节奏**。以下是我认为好的 Vibe Coding 应该遵循的原则：

### 1. 计划先行，小步提交

```
[规划 5min] → [编码 15min] → [验证 5min] → [提交] → 循环
```

每个循环应该：
- **有明确的完成标准**：不是"差不多了"，而是"这个功能能用了"
- **小到可以回滚**：一个循环的改动如果出了问题，可以干净地回退
- **独立可验证**：不需要同时看三个页面才能确认是否正常

### 2. 验证门禁

每次变更后，自动执行检查：

| 变更类型 | 必须验证 |
|---------|---------|
| Schema 变更 | `prisma validate` + `prisma generate` |
| 后端代码 | `tsc` 编译 + API 冒烟测试 |
| 前端代码 | 编译成功 + 页面渲染正常 |
| 依赖变更 | `npm audit` |

这些验证不是可选的，是**每次提交前的标准步骤**。

### 3. 先理解平台，再写代码

在写第一行 Taro 代码之前，应该先确认：
- Taro 小程序支持哪些 CSS 属性（inline style vs className）
- 平台特有的限制（`display: flex` 编译问题）
- 常用的 workaround 是什么

**把这些记录到 CLAUDE.md 的项目说明中**，而不是每次靠记忆或者试错。

### 4. 用户说需求，AI 负责质量

好的分工应该是：

| 谁负责 | 什么 |
|--------|------|
| 用户 | 提出需求、确认效果、决策方向 |
| AI | 实现、测试、审查、发现潜在问题 |

AI 应该在用户发现问题之前，主动审查并提出：
- "这个变更会影响 X 模块，需要同步修改"
- "这个字段没有加索引，大数据量下会慢"
- "这段逻辑没有错误处理"
- "这个状态流转缺少边界判断"

如果总是用户来发现 bug，说明流程出了问题。

### 5. 每次 compaction 前保存关键上下文

上下文压缩是不可避免的，但压缩前应该：
- 把当前决策记录到文档（ADR）
- 把平台限制更新到 CLAUDE.md
- 确保 git 提交信息包含完整的 why（不只是 what）

这样压缩后恢复工作时，新会话能快速进入状态。

### 6. 测试不是可选项

这个项目从开始到现在几乎没有测试。对于进销存系统这种**涉及钱的业务**：

- **库存计算错了就是真金白银的损失**
- 采购入库、销售出库、调拨、盘点这四条链路互相影响库存
- 没有测试意味着每次修改都在赌不会打破平衡

最低要求：每个 service 的核心业务流程要有单元测试，特别是库存变动相关的方法。

### 7. 清晰的迭代节奏

```
Phase N：
  1. 确定本阶段目标（用户确认）
  2. 规划实现步骤
  3. 逐步骤实现 + 验证
  4. 整体 review
  5. 用户确认完成
→ 进入 Phase N+1
```

每个阶段结束时应该有：
- 所有代码已提交
- 核心功能可演示
- 已知 bug 已修复或记录

## 如果是现在重新开始

我会用这样的流程：

1. **初始化**：技术选型、CLAUDE.md 记录平台约束、CI 配置（至少编译检查）
2. **核心数据模型**：先完成 Prisma schema 并严格 validate，再写业务代码
3. **每个模块**：Schema → Service（带测试）→ Controller → 前端页面，按这个顺序
4. **关键链路**：采购入库→库存变化的链路做端到端验证
5. **提交前**：编译检查 + lint + 相关测试 + schema validate
6. **回顾**：每完成 2-3 个模块做一次小回顾，更新文档
